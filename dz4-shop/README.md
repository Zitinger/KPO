Программа написана на Python.

3.5 сервиса (2 бизнес‑микросервиса + API Gateway + "frontend")

- **Orders** - создает заказ и хранит его статус.
- **Payments** - хранит баланс пользователя и пытается оплатить заказ.

Сервисы общаются **асинхронно** через **RabbitMQ**:

- Orders публикует **запрос на оплату** в очередь `shop.payment_requests`.
- Payments читает запрос, делает списание (или отказ) и публикует **результат оплаты** в очередь `shop.payment_results`.

Дополнительно для "реального времени" есть **WebSocket** (WS): клиент подключается к Orders и получает обновления
статуса заказа без опроса.

Чтобы WS-уведомления корректно работали при **нескольких инстансах Orders**, используется **Redis Pub/Sub**: любой
инстанс, который получил результат оплаты, публикует событие в Redis, а оба инстанса слушают Redis и рассылают событие
своим подключенным WS-клиентам.

**Статусы заказа в проекте:**

- `NEW` - заказ создан, ожидается результат оплаты
- `FINISHED` - оплата прошла успешно
- `CANCELLED` - оплата не прошла (например, не хватило денег)

## 1) Структура проекта (основное)

- `docker-compose.yml` - поднимает все сервисы
- `services/orders` - микросервис Orders (HTTP + WS)
- `services/payments` - микросервис Payments (HTTP + воркер)
- `services/gateway` - API Gateway (проксирует запросы к Orders/Payments)
- `edge/` - nginx, который дает один вход (8080) и балансирует WS/HTTP
- `frontend/` - статический фронтенд для проверки (страница /app)

## 4) Быстрая проверка через фронтенд (/app)

1) Открыть страницу: `http://localhost:8080/app/`

2) Указать `user_id` (по умолчанию можно `u1`)

3) (Опционально) Нажать **"Включить уведомления браузера"**  
   Тогда Chrome (или другой браузер) спросит разрешение на Notification API - отправку уведомлений самим браузером.  
   Если не включать - все равно будут toast-уведомления внутри страницы.

4) Нажать **"Создать счет"**

5) Ввести сумму пополнения и нажать **"Пополнить"**

6) Создать заказ:
    - Сумма **меньше или равна** балансу -> статус станет `FINISHED` - покупка оплачена
    - Сумма **больше** баланса -> статус станет `CANCELLED` - покупка отменена

**После создания заказа фронт автоматически подключается к WS для этого `order_id` и показывает уведомления по смене
статуса.**

## 6) WebSocket и уведомления (push)

### WS эндпоинт

WebSocket находится в Orders (через nginx edge):

```
ws://localhost:8080/ws/orders/<order_id>?user_id=u1
```

### Что приходит в WS

Сервер шлет JSON, например:

- snapshot при подключении:

```json
{
  "type": "snapshot",
  "order_id": "...",
  "status": "NEW"
}
```

- обновление статуса:

```json
{
  "type": "status",
  "order_id": "...",
  "status": "FINISHED"
}
```

### Уведомления на фронте

Сделано два варианта:

1) **Toast-уведомления внутри страницы** (всегда работают)
    - уведомления про **смену статуса** держатся ~10 секунд
    - остальные (успешный ответ API, ошибки) держатся ~1-2 секунды

2) **Браузерные уведомления** (Notification API)
    - включаются кнопкой на странице
    - браузер спросит разрешение

## 7) RabbitMQ

Используется direct exchange и две очереди:

- exchange: `shop.direct`
- queue: `shop.payment_requests` (Orders -> Payments)
- queue: `shop.payment_results` (Payments -> Orders)

Идея такая:

- Orders при создании заказа пишет запись в **outbox** и отдельно (в фоне) отправляет сообщение в`shop.payment_requests`
- Payments при получении запроса пишет id в **inbox** (чтобы не обработать второй раз), делает списание в своей БД и
  кладет результат в **outbox**
- Payments отправляет результат в `shop.payment_results`
- Orders читает результат и меняет статус заказа

## 9) Соблюдение критериев

Программа реализована на 10 баллов:

1) **Основные требования к функциональности** реализованы

2) **Микросервисы**  
   Orders и Payments разделены, у каждого свой код и своя бд.

3) **Swagger** и сборка через **Docker** реализованы.

4) **Согласованность и надежность сообщений (RabbitMQ)**  
   Используются outbox/inbox подходы, чтобы:
    - не терять сообщения при рестартах
    - не делать двойное списание при повторной доставке

5) **Реальное отслеживание статуса (WebSocket)**  
   Клиент подключается к WS после создания заказа и получает обновления статуса.

6) **Push-уведомления на фронте**  
   Есть всплывающие уведомления (toast) и опционально браузерные уведомления.

7) **Несколько инстансов бекенда и корректная доставка push**  
   В docker-compose подняты `orders-1` и `orders-2`.  
   Чтобы уведомления доходили независимо от того, какой инстанс обработал событие, используется Redis Pub/Sub:
    - инстанс, который применил результат оплаты, публикует событие в Redis
    - оба инстанса Orders подписаны на Redis и рассылают событие своим WS-клиентам
